# ADR 0001: F2 XAE and ADS backends

## Status

Accepted for the F2 simulation vertical slice.

## Context

The first automation slice must create a TwinCAT project from a template, write
a PLC program, build it, activate it only on the local simulation runtime, and
read a symbol over ADS. It must be single-instance and must not touch real
hardware.

## Decision

- Use the documented XAE DTE Automation Interface through `TcXaeShell.DTE.17.0`
  and `pywin32`.
- Use `TcSysManagerRM` only for experiments; it could open the configuration but
  could not create a PLC project from the standard template in this environment.
- Use the installed TwinCAT 3 standard PLC template, then keep the resulting
  minimal project as `templates/minimal`.
- Build with target platform `TwinCAT OS (x64)`, not `TwinCAT RT (x64)`, because
  this laptop uses `XarMode = UM`.
- Use `pyads` against `127.0.0.1.1.1:851` for the local simulation PLC. If the
  PLC is stopped after activation, the adapter issues ADS `RUN` once.
- Keep XAE and ADS behind ports; the domain and runner do not import COM or
  `pyads` directly.
- Refuse to start a second XAE shell. Do not run hardware activation.
- Allow any future hardware path only through an explicit human approval and a
  different safety policy.

## Consequences

- The real path requires Windows, TwinCAT XAE/XAR, `pywin32`, and `pyads`.
- The first activation on a machine may require TwinCAT runtime licensing. That
  is a machine-level operation and is not automated by the runner.
- The build is synchronous and can take tens of seconds; the ADS read has a
  bounded retry window.
- A local trial license may be generated by TwinCAT outside the workspace. The
  runner does not copy or commit license files.
